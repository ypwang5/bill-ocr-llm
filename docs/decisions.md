## D1 Python 3.11,上限 <3.14

- **背景**:系统默认 Python 是 3.14,另外装了 3.11。查了 PyPI,paddlepaddle 最新 3.3.1 只有 cp39~cp313 的 wheel,没有 3.14 的。
- **备选**:3.12(也支持,但要另外下载)、3.14(装不了 Paddle)
- **选择**:3.11。机器上已经有了,Paddle 支持,生态最成熟。
- **代价**:用不到 3.12+ 的新语法(本项目也用不上)。
- **细节**:`requires-python` 写成 `>=3.11,<3.14`。`uv init` 默认生成的是 `>=3.11`,这样别人用 3.14 也能装上项目,但装 Paddle 时才报错,而且报错信息不会直接说明是 Python 版本的问题。加上上限后,uv 一开始就会拒绝,能早点发现。

## D2 用 uv 管理环境

- **背景**:需要虚拟环境 + 锁定依赖版本,保证别人能复现。
- **备选**:pip + venv(慢,没有原生锁文件)、conda(机器上有,Paddle 社区常用,但更重,容易和系统 Python 混)
- **选择**:uv。一个工具管 Python 版本、虚拟环境、依赖,自带 `uv.lock`。
- **代价**:比 pip 新,部分老教程不适用。项目在 E 盘、缓存在 C 盘,不能用硬链接,会报警告并改成复制,只是安装慢一点。
- **注意**:这台机器的终端会自动激活 conda `(base)`。在本项目里先 `conda deactivate`,避免分不清用的是哪个 python。

## D3 src 布局

- **背景**:包放在哪里。
- **备选**:包直接放根目录(`ocr_extract/`)
- **选择**:`src/ocr_extract/`。必须安装后才能 import,在根目录"碰巧能跑"、换个地方就挂的问题能提前暴露。
- **代价**:多一层目录。

## D4 依赖按步骤加

- **背景**:CLAUDE.md 列了很多依赖(pydantic、paddleocr、openai、fastapi……)。
- **选择**:哪一步用到哪一步再 `uv add`。第 1 步只加了 pytest(dev 依赖)。
- **理由**:每个依赖都能对应到"为什么加";Paddle 安装风险最大,单独一步装,出问题好定位。

## D7 PaddleOCR 关闭 oneDNN

- **背景**:paddleocr 3.7.0 + paddlepaddle 3.3.1(CPU,Windows)用默认参数跑,文本检测推理时报错:
  `NotImplementedError: (Unimplemented) ConvertPirAttribute2RuntimeAttribute not support [pir::ArrayAttribute<pir::DoubleAttribute>] (at ...\onednn\onednn_instruction.cc:118)`
- **怎么定位的**:报错路径里有 `onednn`(Intel CPU 加速库,旧名 MKLDNN)→ 在 paddleocr 源码 `_common_args.py` 里找到 `enable_mkldnn` 开关,关掉后改走 `run_mode="paddle"` → **只改这一个参数**重跑,5 行字全部识别成功,假设成立。
- **备选**:降级 paddlepaddle 到 3.2.x / 3.0.x(可能没这个 bug,但要多试几个版本,还可能和 paddleocr 3.7 不兼容)
- **选择**:`PaddleOCR(enable_mkldnn=False)`
- **代价**:没有 oneDNN 加速,CPU 推理可能慢一些。这张 640×320 的测试图首次 predict 用了 5.8 秒(含预热)。准确的速度留到评估阶段实测,不做猜测。

## 待定:弯曲矫正 UVDoc 开不开(已解决,见 D18)

- **发现**:默认开启 `use_doc_unwarping`。在一张平整的合成图上,它反而把图拉变形了:文字画在 x=40,输出坐标却是 x=0;水平的字,框变成了斜的。关掉后坐标是 x≈38~43,和实际一致。
- **影响**:坐标是"矫正后那张图"上的坐标,不是原图的。1.5 按位置排序、做"关键词右边的值"这类规则时会受影响。
- **为什么现在不决定**:手机拍照、有透视的样本可能正好需要矫正。1.5 用难度样本对照"开 / 关"的准确率后再定。

## D8 无法解析时抛错

- **背景**:`12,5OO.00`、`2026-02-30` 这类值,归一化时该怎么处理。
- **备选**:静默转成 None
- **选择**:抛 `ValueError`,pydantic 会包装成 `ValidationError`,并**一次列出所有不合格的字段**。
- **理由**:可检测的失败好过静默失败。转成 None 的话,B 不知道该重试,D 不知道该回退,评估时也统计不到"校验失败率"。
- **代价**:调用方要处理异常。1.5 的 extractor 负责"只把坏字段设成 null 并记录原因"。

## D9 名字做 NFKC

- **背景**:CLAUDE.md 只要求名字"去首尾空格"。1.2 实测 OCR 会把半角冒号输出成全角,括号也会有同样的问题。
- **备选**:严格按 CLAUDE.md 只去空格
- **选择**:所有字段都先做 NFKC(Unicode 标准化,把全角字符统一成半角)。
- **理由**:`星河科技(北京)` 和 `星河科技(北京)` 是同一个名字,不统一就会判错,所有方案的准确率都会被低估。
- **代价**:偏离了 CLAUDE.md 的原规则。NFKC 也会改动少数特殊字符,比如 `①` 会变成 `1`,在名字里很少见。

## D10 禁止多余字段 + 键必须都出现

- **背景**:LLM 可能把 `payer_name` 拼成 `payer`,也可能漏掉某个键。
- **选择**:
  - `extra="forbid"`:出现不认识的键就报错(用户确认)
  - 5 个字段**不给默认值**:键必须都出现,"找过但没有"要显式写 `null`(**我实现时自己加的,方案里没写,已向用户说明**)
- **理由**:两者都是为了防止"字段名错了或漏了 → 悄悄变成 null → 被当成'没找到'"。
- **代价**:更严格,LLM 格式稍有偏差就会触发重试。2.2 评估时要统计这类失败占多少。

## D11 金额严格校验

- **背景**:OCR 常把小数点认成逗号:`12,500.00` → `12,500,00`。如果直接删掉逗号,会得到 `1250000`,金额放大了 100 倍,而且不报错。
- **选择**:逗号必须在标准千分位的位置上;超过 2 位小数直接报错,不四舍五入。
- **理由**:这是金额最危险的静默失败。人民币只到分,出现第 3 位小数说明某处认错了,四舍五入会把这个信号掩盖掉。
- **验证**:临时把规则放宽成 `[\d,]+`,`12,500,00` 和 `1,2500.00` 两个用例就失败了,说明测试确实能拦住这类错误。

## D12 对账单字段对应

- **背景**:对账单上有多笔交易,"付款人 / 收款人 / 金额"天然对不上。
- **备选**:做成只有一笔交易的明细(和回单几乎重复)
- **选择**:户名 → payer_name;**payee_name 固定为 null**;期末余额 → amount;对账截止日 → date;对账单编号 → serial_no。
- **理由**:明细里到处是对方户名,专门测模型**会不会编一个收款人出来**;明细里的负数是干扰项,标签里的余额永远为正,负数金额问题也就不存在了。
- **代价**:要在文档里说明"对账单的收款人为 null"是设计,不是漏标。

## D13 合成样本规格

- 3 种模板 × 6 档难度 × 4 张 = **72 张**(PROMPTS 建议 60,但 60 除不尽 18 个组合)。
- **每档只施加一种退化**:控制变量,出错时能归因到具体原因。
- **只用 Pillow + numpy**,并显式声明依赖。不用 OpenCV:环境里已有 paddlex 带进来的 `opencv-contrib-python`,再装 `opencv-python` 的话,两个包都会提供 `cv2` 模块,会互相覆盖。
- 印章半透明(alpha 150/255),人眼能透过印章读出下面的字,所以遮挡档的标签仍是真实值。
- 每张图用独立的随机种子 `f"{seed}-{id}"`:改动某一张或新增模板,不会让其他样本跟着变。
- 图片提交进 git(约 10 MB):换一台电脑字体可能不同,固定种子也生成不出完全一样的图,所以评估集要固定下来。

## D14 标准答案独立构造

- **背景**:标签可以用 `ReceiptFields(**rendered).model_dump()` 生成,这样最省事。
- **问题**:这样"归一化(图上写法) == 标签"的测试就成了**自己验证自己**,schema 有 bug 也测不出来。
- **选择**:标准答案直接由源值构造(金额 `f"{amt:.2f}"`、日期 `isoformat()`、名字用半角括号拼出来),图上写法另外随机生成。
- **验证**:临时让标签改用全角括号,189 个用例失败。

## D15 字体缺字

- **发现**:抽样看图时,对账单的"期初余额"显示为 `□6.29`。黑体(simhei)**没有半角 ¥(U+00A5)**,画出来是方框。
- **影响**:如果答案字段用到这个字体和这个符号,OCR 读到的就是乱码,这张样本对所有方案都不公平。
- **选择**:画字之前检查字形,缺字就换成全角 ¥(两者归一化结果相同)。`rendered` 也先过一遍替换,保证标签里记的就是图上画的。
- **测试**:3 种模板 × 3 种字体,检查画过的每个字符字体里都有。临时去掉替换后,恰好是"黑体 × 3 种模板"失败。
- **教训**:测试全过也不代表样本没问题,**一定要亲眼看图**。

## D16 开发集 / 测试集分开

- **背景**:如果一边看 72 张测试集的 OCR 结果一边改规则,A 的准确率会被抬高,等于提前看了考卷。
- **选择**:用 seed=7 另外生成 18 张开发集(每个组合 1 张)。写规则、选 UVDoc 都只看开发集;规则定稿后记下文件哈希,测试集只跑一次,跑完核对哈希没变。
- **效果**:开发集整单全对 78%,测试集 69%。这个落差很正常,说明规则对开发集有一定的"过拟合"。见 D19 的反例。
- **代价**:多 18 张图(2.6 MB)、多跑约 6 分钟 OCR。

## D17 OCR 缓存

- **选择**:`results/ocr_cache/<uvdoc_on|off>/<数据集>/<id>.json`,存图片的 sha256,图片变了就重新识别。
- **理由**:CPU 上单张要 20 秒;更重要的是 1.6 的方案 B 会读同一份缓存,**A 和 B 看到完全相同的 OCR 文字**,两者的差别只来自抽取方法(控制变量)。
- **注意**:缓存里的 `latency_s` 是首次识别的耗时,统计耗时用这个值,不用读缓存的时间。

## D18 UVDoc 保持开启

- **背景**:1.2 发现 UVDoc 会让平整图的坐标偏移。
- **实验**:开发集 18 张,开 / 关各跑一次。整单全对:开 78% vs 关 72%,**只差 1 张**。
- **选择**:保持默认开启。perspective 档两边都是 100%,坐标偏移在开发集上没造成可见的错误。
- **如实说明**:18 张样本里差 1 张,**不足以下结论**,这个决定的依据很弱。
- **测试集里观察到的现象**(未验证):旋转 15° 的对账单,OCR 输出的倾斜角是 0°,说明 UVDoc 或方向矫正把图摆正了;但左边缘的"期末余额"被读成"末余额",可能是矫正时边缘被裁掉了。

## D19 规则 A 的两条"宁可 null"原则

开发集上发现两个**静默错误**,修复原则都是"把静默错误变成可检测的失败",而不是为了提高开发集分数:

1. **分不清归属就输出 null**:水印盖掉了回单的"付款方 / 收款方"标题和付款方户名,只剩收款方户名,规则却把它当成了付款人(对账单分支)。修复:只有在"户名"恰好 1 个、"账号"最多 1 个(说明图上只有一方)时,才走对账单分支。
   - 修复过程中我**改坏过一次**:用"以'户名'结尾"来数户名,把表头"对方户名"也算进去了,6 张对账单的 payer 全部变成 null。改成精确匹配后才恢复。
   - ⚠️ **在测试集上没有完全生效**:receipt_occlusion_02 被盖掉的正好是付款方的户名和账号,剩下"账号 1 个、开户行 2 个",条件照样满足,又取到了收款方户名。我的修复只"对症"了开发集那一个例子,**这是对开发集过拟合**。按规定测试集结果出来后不再改规则,这个问题作为失败案例记录。
2. **OCR 金额必须带角分**:印章把 `220,957.09` 拆成 `RMB220,957` 和 `09`,规则接受了 `220957.00`。票据打印的金额都带两位小数,缺了就报错。
   - ✅ **在测试集上生效了**:receipt_occlusion_03 的 1.07 被拆成 `RMB107`,如果没有这条规则,就会得到 107.00,**放大 100 倍**。
- **故意不做**:不兼容 `RM8 2,297,511.20` 这种写法。如果改成"从字符串里搜数字",会搜出 82,297,511.20,用看得见的失败换来看不见的灾难。

## D20 方案 B 的提示词 v1 与校验

- **结构**:system(角色 / 输入说明 / 字段定义表 / 干扰项 / 输出规则)+ user(OCR 文本放进 `<ocr_text>` 标签)+ retry(错误原因)。三个文件放在 `prompts/extract_v1/`,算 sha256 指纹。
- **字段定义给到和规则 A 同样多的领域知识**(哪个标签对应哪个字段、哪些是干扰项),这样对比才公平。
- **金额允许用大写核对修正**(用户选了 a):依据在单据上,不算编造。备选 b"严格照抄"更安全,但 B 在金额上就基本不会比 A 强。
- **户名照抄,不许改字**:模型不知道正确的字是哪个,改了也是猜。
- **v1 故意不加**:few-shot 示例、坐标、引用原文作证据。留给 2.x 做提示词优化的对照实验。
- **校验**:JSON 模式 + `ReceiptFields`(extra=forbid,5 个键都必须有)。不合格把错误原因发回去重试 1 次;再不合格只丢坏字段(D8)。网络错误由 SDK 重试(max_retries=2),和格式重试分开统计。
- **temperature=0**,原始输出全部存进 predictions.jsonl。

## D21 开发集上加了"分不清哪一方就填 null"

- **发现**:开发集 receipt_occlusion_00,"付款方/收款方"标题和左栏户名被水印盖掉。纯文本里只剩一个户名,模型按出现顺序当成了付款人(静默错误)。
- **根因**:`OcrResult.text` 只有文字,没有坐标,**左右栏的位置信息丢了**。
- **选择**:在提示词里加一条通用规则:分不清就两个都填 null。这是"把静默错误变成可检测的失败",和 D19 同一个原则。
- **代价**:SUBSET10 的 receipt_occlusion_01,收款人那个户名原本可能"猜对",现在是 null。
- **备选**:把坐标(或"左栏/右栏")放进 OCR 文本。更根本,但提示词变长,v1 不做,作为 v2 的候选。
- **之后冻结**:sha256 前缀 `b081e5d91902`,SUBSET10 只跑了这一次。

## D22 deepseek-flash 默认会"思考"

- **发现**:usage 里 `reasoning_tokens` 不为 0。清晰单约 60,遮挡单 300~950。思考 token 按输出价计费。
- **影响**:单张成本约 0.002 元、LLM 耗时 P95 约 2.6~5.4 秒,都比"不思考"高;好处可能是难单子上更谨慎(未验证,没做关闭思考的对照)。
- **当前选择**:保持默认,如实记录。是否关闭思考、换 `deepseek-v4-pro`,留到 2.2 有完整数据后再比。
- **第 2 天风险**:`.env` 里 `LLM_MODEL_VISION` 也填的 deepseek-flash,它很可能不支持图片输入,方案 C 可能需要别家的多模态模型。待 2.1 实测。

## 局限:合成数据的已知问题

| 问题 | 影响 | 为什么不修 |
|---|---|---|
| 对账单手续费按余额比例算,余额大时手续费上万元(如 -12,733.79) | 不真实,但不是要抽取的字段,不影响评估 | 改生成器会让已经固定的测试集跟着变 |
| 只有 3 种版式,字体是电脑字体 | 规则 A 对着模板写,结果偏乐观;结论只能看**相对比较** | 合成数据的固有局限,上线前需要内网真实样本验证 |
| 每张图只有一种退化 | 真实照片常常模糊 + 倾斜 + 印章同时出现 | 故意如此:每档单一退化,才能回答"哪种退化伤害哪个方案" |
| 对账单 4 张遮挡图都只压金额 | 遮挡档对账单的户名没有被测到 | 同上,不改测试集 |
| SUBSET10 只有 10 张 | 80% vs 50% 差 3 张,**统计上不稳** | 按手册先小样本对比,2.2 在 72 张全量上再比 |

## D23 方案 C:deepseek-flash 看原图

- **背景**:1.6 担心 DeepSeek 不支持图片。实测 `deepseek-flash` 支持(带图读对流水号,不带图回答"看不到图片"),`deepseek-v4-pro` 忽略图片。
- **图片**:原图 PNG、base64,最长边 >1600 才缩小。实测 512/1024/2048 约 210/440/1000 token,三种都读对 20 位发票号;测试集原图最长边 ≤1276。不用 JPEG,怕压缩糊掉小数点。
- **提示词**:`prompts/vlm_v1/`,字段定义和 B 完全相同,只改输入说明和两条规则(看不清不猜、按版面位置判断归属)。开发集跑完没有改动就冻结(sha256 前缀 `0082b994ac41`)。
- **代价**:同一个模型同时做 B 和 C,"C 比 B 好/差"的结论只代表 deepseek-flash,换更强的视觉模型结论可能变。
