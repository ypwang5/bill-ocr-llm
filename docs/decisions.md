## D1 Python 3.11,上限 <3.14

- **背景**:系统默认 Python 是 3.14,另外装了 3.11。查了 PyPI,paddlepaddle 最新 3.3.1 只有 cp39~cp313 的 wheel,没有 3.14 的。
- **备选**:3.12(也支持,但要另外下载)、3.14(装不了 Paddle)
- **选择**:3.11。机器上已经有了,Paddle 支持,生态最成熟。
- **代价**:用不到 3.12+ 的新语法(本项目也用不上)。
- **细节**:`requires-python` 写成 `>=3.11,<3.14`。`uv init` 默认生成的是 `>=3.11`,这样别人用 3.14 也能装上项目,但装 Paddle 时才报错,而且报错信息不会直接说明是 Python 版本的问题。加上上限后,uv 一开始就会拒绝,能早点发现。

## D2 用 uv 管理环境

- **背景**:需要虚拟环境 + 锁定依赖版本,保证别人能复现。
- **备选**:pip + venv(慢,没有原生锁文件)、conda(机器上有,Paddle 社区常用,但更重,容易和系统 Python 混)
- **选择**:uv。一个工具管 Python 版本、虚拟环境、依赖,自带 `uv.lock`。
- **代价**:比 pip 新,部分老教程不适用。项目在 E 盘、缓存在 C 盘,不能用硬链接,会报警告并改成复制,只是安装慢一点。
- **注意**:这台机器的终端会自动激活 conda `(base)`。在本项目里先 `conda deactivate`,避免分不清用的是哪个 python。

## D3 src 布局

- **背景**:包放在哪里。
- **备选**:包直接放根目录(`ocr_extract/`)
- **选择**:`src/ocr_extract/`。必须安装后才能 import,在根目录"碰巧能跑"、换个地方就挂的问题能提前暴露。
- **代价**:多一层目录。

## D4 依赖按步骤加

- **背景**:CLAUDE.md 列了很多依赖(pydantic、paddleocr、openai、fastapi……)。
- **选择**:哪一步用到哪一步再 `uv add`。第 1 步只加了 pytest(dev 依赖)。
- **理由**:每个依赖都能对应到"为什么加";Paddle 安装风险最大,单独一步装,出问题好定位。

## D5 schema 提前到合成样本之前

- **背景**:PROMPTS.md 原来把 schema 归一化放在 1.4(和 OCR 封装、方案 A 一起),排在合成样本 1.3 之后。
- **备选**:按原手册走
- **选择**:新增 1.3 schema,合成样本改为 1.4,后续编号顺延。
- **理由**:
  1. 合成样本要保存标准答案,标签格式(金额 `12500.00`、日期 `2026-03-15`)应该先由 schema 定下来,否则可能返工
  2. 能写"渲染写法 → 归一化 = 标签"的测试,同时检查生成器和归一化
  3. 原 1.4 塞了 4 件事,太满
- **代价**:第 1 天多一步,约 30~45 分钟。
- **同时决定保留的 PROMPTS 原有安排**(我原计划不如它):PaddleOCR 在 1.2 就装(风险最大的先排掉);评估框架留到第 2 天(免得写两遍)。

## D6 目录骨架一次建好

- **背景**:D4 里我选了"用到哪个目录再建",但 PROMPTS.md 1.2 要求按 CLAUDE.md 建好骨架。
- **选择**:一次建好。Python 子包放空的 `__init__.py`,数据和输出目录放 `.gitkeep`,因为 git 不记录空目录。
- **理由**:一开始就能看到项目全貌,和手册保持一致。
