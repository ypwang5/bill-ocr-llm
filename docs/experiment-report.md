## 4. 最意外的发现

1. **10 张的结论被 72 张推翻**:SUBSET10 上 B 80% > C 70%,全量上 C 85% > B 83%。10 张里差 1 张就是 10 个点。
2. **C 在 CPU 环境下最快**:1.5 秒 vs B 的约 21 秒,因为 B 的瓶颈是 CPU 上的 OCR,不是 LLM。"多模态更慢"的假设在这台机器上不成立。
3. **B 和 C 几乎不在同一处出错**:字段错误里两者都错的只有 2 个,只有 B 错 18 个、只有 C 错 10 个。理想融合(每个字段挑对的)上限是 70/72 = 97%。
4. **B 错时大多是 null,C 错时全是静默错误**。C 的整单全对率更高,但更危险。
5. **C 的编号是短板**(90%),而 OCR 读编号几乎没错。C 的 6 个编号错误里 5 个能被格式规则拦住(发票号 20 位、回单 HX+14 位)。
6. **"允许用大写修正"在没有大写的对账单上被滥用**,产生了 B 唯一一个金额静默错误。

## 5. 按场景该用谁(不美化)

| 场景 | 推荐 | 依据 |
|---|---|---|
| 清晰、平整的单据 | A 或 B | A、B 都 100%,A 免费;C 反而会认错形近字(clean 92%) |
| 模糊 | B | 75% vs C 58%;OCR 读得到,LLM 能读懂被认坏的千分位 |
| 遮挡 | C | 83% vs B 33%;OCR 读不到的,多模态看得到 |
| 对账单 | B | 96%;C 的"沭"错误集中在对账单 |
| 要求不能静默出错 | B,外加 C 补空 | B 的错误多是 null |
| 要求快 | C | 不受 CPU OCR 拖累 |

## 6. 局限
- 合成数据,版式只有 3 种,字体干净;结论只能看相对比较。
- 文本和视觉用的是同一个模型 deepseek-flash,换更强的视觉模型结论可能变。
- 72 张仍不大,差 1~2 张就是 1~3 个百分点;同一配置重跑结果也会有小波动(temperature=0 也不完全确定)。
- OCR 只跑了 CPU;有 GPU 时 B 的耗时会大幅下降,"C 最快"的结论不成立。
