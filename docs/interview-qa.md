# 面试问答

> 参考回答要基于本项目的真实数据。标【待数据】的地方,等实验跑完后用实测数字替换。

## 一、项目总览

### Q: 这个项目解决什么问题?为什么银行要做?
银行每天大量转账回单、发票、对账单要人工录入,慢且易错。项目从票据图片抽取 5 个字段(付款人、收款人、金额、日期、流水号)输出 JSON。银行场景的特殊性:金额不能错(宁可 null 转人工)、数据不出内网(LLM 走 OpenAI 兼容接口,可换本地模型)、量大要算成本(所以做融合路由)。

### Q: PaddleOCR 内部怎么工作?
流水线:(可选预处理:整图方向、弯曲矫正)→ **文本检测**(框出每行字)→(可选行方向分类)→ **文本识别**(读出每个框的字并给置信度)。输出是"框坐标 + 文字 + 置信度"。它只认字,不理解语义。

## 二、方案对比

### Q: OCR 认错一个字,规则方案和 LLM 方案有什么区别?
规则方案可能**截取一部分**,比如 `12,5OO.00` 被正则截成 `12,5` → 125,错了还不报错。LLM 能结合上下文把形近字母纠正回数字(O→0),但"数字认成另一个数字"(8→3)它也救不回来。【待数据:A/B 在模糊样本上的金额准确率】

### Q: 为什么要求模型找不到就输出 null?
null 是**可检测的失败**:系统马上发现,转人工,代价是几分钟补录。编造是**静默失败**:格式合法能通过校验,流进下游,可能要到对账不平才发现,代价是资金和合规风险。另外 null 也是方案 D 的回退信号,模型如果编造,D 就不知道该回退。

### Q: 印章遮挡时,OCR+LLM 和多模态各有什么问题?
OCR+LLM 丢失版面信息,会把印章里的字(如"XX银行业务专用章")当成收款人。多模态能看到颜色和叠层,有机会透过半透明印章读出原字,但完全看不清时会编造一个合理的名字,而且从输出上分不出是"看到的"还是"猜的"。【待数据:印章组的失败案例】

### Q: 融合路由为什么是先 B 后 C?
1. **成本**:D 成本 = B + 回退比例 × C。大部分票据清晰,B 就能搞定,只有少数走 C。【待数据:实测回退比例、单张成本】
2. **回退信号**:B 有 OCR 置信度和校验结果,能报告"我不确定";C 没有置信度,自信编造时格式也正确,很难判断何时该回退。
3. **为什么不两个都跑**:默认成本太高。但结果不一致本身是很强的风险信号,高金额单据可以双跑交叉校验,作为后续改进。

## 三、工程化

### Q: 别人怎么复现你的环境?
用 uv 管理。`uv.lock` 锁住所有依赖的精确版本,`.python-version` 和 `requires-python = ">=3.11,<3.14"` 约束 Python 版本。对方 clone 后跑 `uv sync` 就行,没有 3.11 的话 uv 会自动下载。上限 `<3.14` 是因为 paddlepaddle 3.3.1 没有 3.14 的 wheel,加上它可以尽早失败,不用等到装 Paddle 时才报错。

### Q: 为什么提交 uv.lock,不提交 .venv?
lock 是"配方",跨平台、体积小;`.venv` 是按配方装出来的结果,里面有 Windows 的 exe 和绝对路径,跟平台绑定,换台机器用不了,而且装上 Paddle 后有好几个 GB。

### Q: API Key 怎么管理?泄露了怎么办?
只放在 `.env`,`.gitignore` 排除它,仓库只提交没有值的 `.env.example`。如果泄露,第一步是**立刻作废 key**,而不是删文件。git 历史会一直保留它,GitHub 上的扫描机器人几分钟就能抓到。然后查调用记录和账单,按流程上报安全团队,再考虑清理历史和加上提交前的密钥扫描。
