# 面试问答

> 参考回答要基于本项目的真实数据。标【待数据】的地方,等实验跑完后用实测数字替换。

## 一、项目总览

### Q: 这个项目解决什么问题?为什么银行要做?
银行每天大量转账回单、发票、对账单要人工录入,慢且易错。项目从票据图片抽取 5 个字段(付款人、收款人、金额、日期、流水号)输出 JSON。银行场景的特殊性:金额不能错(宁可 null 转人工)、数据不出内网(LLM 走 OpenAI 兼容接口,可换本地模型)、量大要算成本(所以做融合路由)。

### Q: PaddleOCR 内部怎么工作?
流水线:(可选预处理:整图方向、弯曲矫正)→ **文本检测**(框出每行字)→(可选行方向分类)→ **文本识别**(读出每个框的字并给置信度)。输出是"框坐标 + 文字 + 置信度"。它只认字,不理解语义。

## 二、方案对比

### Q: OCR 认错一个字,规则方案和 LLM 方案有什么区别?
规则方案可能**截取一部分**,比如 `12,5OO.00` 被正则截成 `12,5` → 125,错了还不报错。LLM 能结合上下文把形近字母纠正回数字(O→0),但"数字认成另一个数字"(8→3)它也救不回来。【待数据:A/B 在模糊样本上的金额准确率】

### Q: 为什么要求模型找不到就输出 null?
null 是**可检测的失败**:系统马上发现,转人工,代价是几分钟补录。编造是**静默失败**:格式合法能通过校验,流进下游,可能要到对账不平才发现,代价是资金和合规风险。另外 null 也是方案 D 的回退信号,模型如果编造,D 就不知道该回退。

### Q: 印章遮挡时,OCR+LLM 和多模态各有什么问题?
OCR+LLM 丢失版面信息,会把印章里的字(如"XX银行业务专用章")当成收款人。多模态能看到颜色和叠层,有机会透过半透明印章读出原字,但完全看不清时会编造一个合理的名字,而且从输出上分不出是"看到的"还是"猜的"。【待数据:印章组的失败案例】

### Q: 融合路由为什么是先 B 后 C?
1. **成本**:D 成本 = B + 回退比例 × C。大部分票据清晰,B 就能搞定,只有少数走 C。【待数据:实测回退比例、单张成本】
2. **回退信号**:B 有 OCR 置信度和校验结果,能报告"我不确定";C 没有置信度,自信编造时格式也正确,很难判断何时该回退。
3. **为什么不两个都跑**:默认成本太高。但结果不一致本身是很强的风险信号,高金额单据可以双跑交叉校验,作为后续改进。

## 二·五、PaddleOCR

### Q: PaddleOCR 输出什么?你怎么用?
每行三样:文字 `rec_texts`、置信度 `rec_scores`(整行一个 0~1 的分数)、坐标 `rec_polys`(4 个角点,可以是斜四边形)。文字给规则和 LLM 用;坐标用来排出阅读顺序,规则方案还用它做"关键词右边的值"配对;置信度是融合方案的回退信号之一。

### Q: 规则方案怎么把"金额"和它的值配对?票据拍歪了怎么办?
OCR 给出的是独立的框,先用坐标配对:中心 y 差小于半个行高、在关键词右边、距离最近。倾斜 15° 时,相距 300px 的两个框 y 会偏约 80px,会判错行甚至配到下一行的值。做法是用每个框上边的斜率算出角度,取中位数作为整图倾斜角,把坐标反向旋转后再配对。PaddleOCR 自带的方向分类只处理 0/90/180/270°,不管小角度。【待数据:1.5 倾斜样本上的实际效果】

### Q: 置信度高就说明识别对了吗?
不是。我的冒烟测试里 `¥12,500.00` 被识别成 `12,500.00`,漏了 ¥,置信度却是 **0.998**。置信度只反映字形认得准不准,不反映有没有漏字,也管不住后面 LLM 把字段放错。所以融合方案除了置信度,还要看 schema 校验、关键字段是否为 null、业务规则(比如回单的大写和小写金额是否一致)。比如金额被截成 125,schema 拦不住(它是合法数字),只有大写金额对不上才能拦住。

### Q: PaddleOCR 部署遇到过什么问题?
paddleocr 3.7.0 + paddlepaddle 3.3.1 在 Windows CPU 上,默认开启的 oneDNN 加速导致文本检测报 `NotImplementedError ... onednn_instruction.cc`。排查过程:报错路径里有 onednn → 在源码里找到 `enable_mkldnn` 开关 → **只改这一个参数**重跑,成功,确认根因。没有同时改别的设置,是为了控制变量,避免背上不需要的副作用。另一个发现:默认开启的弯曲矫正(UVDoc)在平整的图上反而让坐标偏移(x 从 40 变成 0),要不要关等难度样本对照后再定。

### Q: 2.x 和 3.x 有什么区别?
3.x 用产线式的 `predict()`,`.ocr()` 已被标为 deprecated;参数改名(如 `use_angle_cls` → `use_textline_orientation`);默认模型是 PP-OCRv6;内置文档方向分类和弯曲矫正;`paddleocr` 不再自动依赖 `paddlepaddle`,要单独装。这些我是读装好的源码确认的。

## 二·六、字段 schema 与归一化

### Q: 金额为什么用 Decimal 不用 float?
float 是二进制近似值,`0.1+0.2` 得到 `0.30000000000000004`,对账逐分比较时会对不平。我用 Decimal 并 `quantize` 到 2 位;序列化成 JSON 时金额输出为**字符串** `"12500.00"`,避免别的程序读进来后又转成 float。

### Q: 归一化为什么会影响评估?会不会归一化过头?
评估用完全匹配。`¥12,500.00` 和 `12500.00`、全角括号和半角括号,其实都是同一个值,不归一化会判错,准确率被低估,而且对输出写法比较自由的 LLM 方案不公平。但归一化也可能过头:比如流水号如果把 O 都换成 0,本来不同的值会被判成相同,准确率被高估。所以每条规则我都会问:**这是在统一写法,还是在掩盖错误?** 流水号我就没做 O→0 替换。

### Q: OCR 把小数点认成逗号怎么办?
`12,500.00` 被认成 `12,500,00` 时,如果直接删逗号会得到 1250000,**放大 100 倍且不报错**。我的金额校验要求逗号必须在标准千分位的位置上,最后一组必须是 3 位,所以这种情况会报错,触发重试或回退。超过 2 位小数也直接报错,不四舍五入,因为人民币只到分,出现第 3 位小数说明认错了。我用变异测试验证过:把规则放宽后,这个用例马上失败。

### Q: LLM 输出字段名拼错或漏了键怎么办?
pydantic 设置 `extra="forbid"`,并且 5 个字段都不给默认值。拼错(如 `payer`)会报 `extra_forbidden`,漏键会报 `missing`。如果宽松处理,字段会悄悄变成 null,被当成"没找到",既不会重试也不会回退。代价是格式稍有偏差就要重试、多花 token,所以提示词里要求 5 个键全部输出,评估时统计格式重试的占比。【待数据:2.2 格式重试率】

### Q: 你怎么证明测试是有效的?
变异测试:故意把代码改坏,看对应的测试会不会失败。去掉 NFKC 后,6 个全角用例失败;千分位规则放宽后,`12,500,00` 用例失败。另外我还发现自己第一版测试里的"全角"用例其实写成了半角,什么也没测到,后来改成 `（` 这样的 Unicode 转义写法。

## 二·七、合成数据

### Q: 为什么用合成数据?标签怎么来的?
不能用真实银行数据,而且人工标注又慢又可能标错。合成数据是先随机生成答案,再画到图上,标签 100% 准确。关键细节:标签由源值**独立构造**,不经过被测的归一化函数,否则"归一化(图上写法) == 标签"的测试就成了自己验证自己。我用变异测试证明过:让标签改用全角括号,189 个用例失败。

### Q: 合成数据和真实数据差距多大?你的结论还可信吗?
差距在:版式只有 3 种、电脑字体太干净、每张图只有一种退化、名字词表小、印章简单。所以结论只能当作**上限**和**相对比较**:可控的好处是每档只有一种退化,能回答"模糊对哪个方案伤害最大"。规则方案是对着模板写的,在这批数据上会偏乐观,我会在报告里明确写出来。上线前需要在内网用一小批脱敏真实样本做验证。

### Q: 规则方案 95%,为什么还要大模型?
规则是看着这 3 种模板写的,就像提前看过考卷。换一家银行的版式,规则就失效。银行要对接几百家机构,规则的维护成本会失控;大模型的价值是对没见过的版式也能用。【待数据:1.5 A 的实际准确率】

### Q: 对账单上模型填了一个收款人,但对账单本来没有收款人,这算什么错?
模型幻觉 / 版面理解错,而且比"认错一个字"更危险:编出来的是明细里真实存在的交易对手,名字完全合法,任何校验都拦不住。null 反而是安全的,能转人工。所以我除了字段准确率,还统计**幻觉率**(标签为 null、模型却输出了值)。对账单的 payee_name 固定为 null,就是专门为测这个设计的。

### Q: 做合成数据时踩过什么坑?
1. 黑体没有半角 ¥ 的字形,画出来是方框。测试是全部通过的,是我**亲眼看图**才发现的。修复后加了"所有模板 × 所有字体不缺字"的测试。
2. 遮挡档随机选目标,8 张里只抽中 2 张压收款人,样本太少,改成轮流。这是按样本分布调整,不是按方案结果挑样本。
3. 想装 OpenCV 做透视变换,发现 paddlex 已经带了 `opencv-contrib-python`,再装 `opencv-python` 会因为都提供 `cv2` 而互相覆盖,所以改用 Pillow + numpy 实现。

## 三、工程化

### Q: 别人怎么复现你的环境?
用 uv 管理。`uv.lock` 锁住所有依赖的精确版本,`.python-version` 和 `requires-python = ">=3.11,<3.14"` 约束 Python 版本。对方 clone 后跑 `uv sync` 就行,没有 3.11 的话 uv 会自动下载。上限 `<3.14` 是因为 paddlepaddle 3.3.1 没有 3.14 的 wheel,加上它可以尽早失败,不用等到装 Paddle 时才报错。

### Q: 为什么提交 uv.lock,不提交 .venv?
lock 是"配方",跨平台、体积小;`.venv` 是按配方装出来的结果,里面有 Windows 的 exe 和绝对路径,跟平台绑定,换台机器用不了,而且装上 Paddle 后有好几个 GB。

### Q: API Key 怎么管理?泄露了怎么办?
只放在 `.env`,`.gitignore` 排除它,仓库只提交没有值的 `.env.example`。如果泄露,第一步是**立刻作废 key**,而不是删文件。git 历史会一直保留它,GitHub 上的扫描机器人几分钟就能抓到。然后查调用记录和账单,按流程上报安全团队,再考虑清理历史和加上提交前的密钥扫描。
