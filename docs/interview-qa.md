# 面试问答(32 题)

> 所有数字来自本项目的真实实验(测试集 72 张,`results/20261024_004217_benchmark_test/`)。合成数据,结论看相对比较。

## 一、项目总览与 OCR 原理

### Q1 用一分钟介绍这个项目。
从银行票据图片(转账回单、发票、对账单)里抽取付款人、收款人、金额、日期、编号 5 个字段,输出 JSON。对比了四种方案:A 是 PaddleOCR + 规则,B 是 OCR 文本交给大模型,C 是多模态大模型直接看图,D 是先走 B、B 有字段为空时再调 C 补。72 张合成测试集上,整单全对率 A 69%、B 83%、C 85%、D 90%;我还单独统计了"静默错误"(输出了错的值),因为银行场景里错值比空值危险得多:D 的安全版本静默错误只有 5 个,比任何单一方案都少。最后用 FastAPI 做成了接口和网页。

### Q2 为什么银行要做这件事?有什么特殊要求?
大量票据要人工录入,慢且容易错。特殊要求三条:① 金额不能错,宁可留空转人工;② 数据不能出内网,所以 LLM 调用统一走 OpenAI 兼容接口,可以换成本地部署的模型;③ 量大要算成本,所以做了融合路由,只有 8% 的单据需要多调一次模型。

### Q3 OCR 是什么?PaddleOCR 内部分哪几步?
OCR 把图片变成文字,只认字,不懂意思。PaddleOCR 是一条流水线:(预处理:整图方向分类、弯曲矫正)→ **文本检测**(框出每一行字的位置)→(文本行方向分类)→ **文本识别**(读出每个框里的字,给一个 0~1 的置信度)。输出是"文字 + 置信度 + 四个角点坐标"。

### Q4 置信度高就说明识别对了吗?
不是。冒烟测试里 `¥12,500.00` 被识别成 `12,500.00`,漏了 ¥,置信度却是 0.998。置信度是整行一个分数,只反映"字形认得准不准",管不了三件事:漏字、认成另一个合法的字(澍 → 洲,模型照样自信)、以及 OCR 没错但字段被放错了位置。本项目里 B 照抄的 OCR 错字,所在行的置信度都不低,所以融合路由不能只靠置信度。

## 二、PaddleOCR 实践

### Q5 PaddleOCR 部署遇到过什么问题?
paddleocr 3.7.0 + paddlepaddle 3.3.1 在 Windows CPU 上,默认开启的 oneDNN 加速导致检测报 `NotImplementedError ... onednn_instruction.cc`。报错路径里有 onednn → 在源码里找到 `enable_mkldnn` 开关 → 只改这一个参数重跑,成功。只改一处是为了控制变量。另外,3.x 用 `predict()`,旧的 `.ocr()` 已标为 deprecated,`paddleocr` 也不再自动安装 `paddlepaddle`,这些都是读已安装版本的源码确认的。

### Q6 规则方案怎么把"金额"和它的值配对?票据拍歪了怎么办?
OCR 输出的是一个个独立的框,"金额"和 `12,500.00` 往往是两个框,所以先用坐标配对,再用正则清洗值。配对条件:两框中心 y 差小于半个行高、在关键词右边、距离最近。歪 15° 时,相距 300px 的两个框 y 会差约 80px,会配到下一行的值。做法是用每个框上边的斜率算角度,取**中位数**当整图倾斜角,把坐标反向旋转摆正后再配对。测试集 rotate 档 A 92%。

### Q7 OCR 的瓶颈在哪?
CPU 上单张 P50 19.3 秒、P95 27.3 秒,是整个 B/D 方案耗时的 90% 以上(LLM 只要 1~2 秒)。我做了两件事:按图片 sha256 把 OCR 结果缓存到磁盘,A、B、D 读同一份,既省时间又保证对比公平;服务启动时加载一次模型,推理加锁串行。上线要用 GPU 或把 OCR 拆成独立服务横向扩展。

### Q8 弯曲矫正(UVDoc)开不开?你怎么决定的?
冒烟测试发现它在平整图上会让坐标偏移。我在开发集上开 / 关各跑一次:开 78%、关 72%,只差 1 张。所以保持默认开启,但在决策记录里写明"证据弱"。

## 三、多模态

### Q9 多模态模型是怎么"看图"的?为什么图片耗 token?
图片被切成很多小方块(patch),每块编码成一个向量,当成"图片 token",和文字 token 一起送进模型。图越大方块越多:实测最长边 512/1024/2048 约 210/440/1000 token。我传原图 PNG(最长边 ≤1600 才缩小),一张约 500 token。不用 JPEG,是怕压缩糊掉小数点。

### Q10 多模态准确率更高,为什么不全用多模态?
C 整单 85%,比 B 高 2 个点,但静默错误最多:10 个,B 只有 6 个。其中"沐"在 3 张图上都被看成"沭",清晰图上也错,是系统性错误;20 位发票号会漏一位;模糊图上 H 会看成 8。这些错误格式都合法,很难被发现。另外 C 没有"我不确定"的信号,B 有(字段为空、OCR 置信度)。D 只用 8% 的回退,就比 C 高 5 个点。

### Q11 多模态在哪里明显更强?
遮挡档:C 83%,B 只有 33%。印章、水印盖住的那一行 OCR 根本没识别出来,B 看不到;C 直接看图,能透过半透明的印章读出来。C 不经过 OCR,在 CPU 环境下也是最快的:P50 1.5 秒。

### Q12 C 和 B 用的是同一个模型吗?这影响结论吗?
是,都是 deepseek-flash,它支持图片输入(实测带图能读出流水号,不带图回答"看不到图片")。好处是 B、C 的差别只来自输入是文字还是图片;代价是"多模态不如/优于 OCR+LLM"的结论只代表这一个模型,换更强的视觉模型可能会变。

## 四、提示词

### Q13 你的提示词是怎么设计的?
B 的提示词分五部分:① 角色:只依据给定文本;② 输入说明:文本有错字,印章水印会混进来,表格被拆成一格一行;③ 字段定义表:每种票据上对应哪个标签,给的领域知识和规则 A 一样多,保证公平;④ 干扰项:发票的不含税金额、对账单的期初余额等;⑤ 输出规则:固定 5 个键,户名照抄不改字,找不到就填 null。C 的提示词字段定义一字不改,只改和输入有关的部分(看不清的字不要猜、按版面位置判断归属)。提示词放在独立文件里,算 sha256 写进实验配置。

### Q14 调提示词时遇到过什么问题?
开发集上,水印盖掉了"付款方/收款方"标题,只剩一个户名,模型按出现顺序把它当成了付款人。根因是纯文本里没有坐标,左右栏的信息丢了。我加了一条通用规则"分不清哪一方就两个都填 null",没有针对这张图写特例。代价是测试集上一个本来能猜对的收款人变成了 null。

### Q15 允许模型"修正"OCR 错误,是好是坏?
有好有坏。我允许它用同一张单上的大写金额修正被认坏的小写金额:模糊档千分位被认成小数点的 `¥3.313,805.85`,B 全部修对了,B 的金额准确率 97%,A 只有 82%。但在没有大写的对账单上它越界了:`期末余额:294银行`(印章压住)被"修"成了 2.94,正确是 2.04,思考了 3777 个 token,这是 B 唯一一个金额静默错误。改进:提示词明确"只有存在大写金额时才允许修正"。

### Q16 LLM 输出的格式怎么保证?
三层。接口开 JSON 模式,保证是合法 JSON;pydantic 的 `ReceiptFields` 要求 5 个键都在、不能有多余的键(`extra="forbid"`)、金额日期能解析;校验不过,就把错误原因连同模型自己的输出一起发回去,重试一次;再不过,就只丢坏字段。测试集上 B、C 共 144 次调用,格式重试 0 次。

### Q17 LLM 有没有编造?
对账单上从来没有编过收款人,幻觉率是 0。有两个灰色案例:截止日被盖住,模型用"对账期间……至 04-14"的结束日期去填,碰巧对了,但这是推断;另一个就是上面"294 → 2.94"的越界修正。

## 五、评估

### Q18 你用了哪些指标?为什么不只看准确率?
字段准确率、整单全对率、静默错误率、留空率、幻觉率、格式重试/失败率、P50/P95 耗时、单张成本。只看准确率会把两种错混在一起:静默错误(输出错值,下游发现不了)和留空(能被发现、能转人工)。C 的整单准确率比 B 高,静默错误却多 4 个;只看准确率就会选错方案。

### Q19 为什么用字段级而不只是整单级?归一化为什么会影响结果?
整单级只告诉你"错了几张",字段级告诉你"错在哪":C 的编号只有 90%,是它的短板。归一化方面:`12500` 和 `12500.00` 不归一化会被判成不同,测的就成了格式习惯,对改写更多的 LLM 不公平;但归一化过头也会把错的判成对的,比如流水号我就没有做 O → 0 的替换。三个方案共用同一套 schema 归一化。

### Q20 你怎么保证评估可信、没有"作弊"?
三套独立种子:开发集 18 张用来调规则和提示词,调参集 36 张用来选 D 的配置,测试集 72 张只用于报告。提示词定稿后记 sha256 冻结;D 的选参规则在看结果之前写下;两套 D 配置在跑测试集之前写进代码。还有一处轻微泄露也如实记录了:"编号格式校验"这个候选是看了测试集的错误才想到的,但调参集没有选它。

### Q21 有没有结论被推翻过?
有。最早 10 张对比时,B 80% 比 C 70% 好;全量 72 张时变成 C 85% 比 B 83% 略好。10 张里差 1 张就是 10 个百分点。另外,同一配置跑两次,C 的字段结果也不完全一样(temperature=0 也不保证确定)。所以我以全量结果为准,并在报告里写明 72 张仍然偏少。

### Q22 每种方案最典型的失败是什么?
A:OCR 认错生僻字后照抄(5 个,静默);水印盖掉标题后把收款人当付款人(1 个,静默);千分位被认坏,被严格校验拦下(null)。B:和 A 一样的 5 个 OCR 错字(B 也只能照抄);越界修正金额(1 个);信息被遮挡,文本里没有(14 个,都是 null)。C:形近字"沐 → 沭"(系统性)、编号漏位或 H → 8(6 个,都是静默)。

### Q23 合成数据和真实数据差距多大?结论还可信吗?
差距:版式只有 3 种、电脑字体太干净、每张图只有一种退化、印章简单。所以结论只能看**相对比较**,比如"遮挡伤 B 最重、模糊伤 C 最重"。规则方案是对着模板写的,结果偏乐观。上线前要在内网用一批脱敏的真实样本重新评估,重点看版式没见过时 A 掉得多快。

## 六、融合方案

### Q24 融合路由怎么设计的?效果如何?
先走 B;只要 B 校验失败,或者关键字段为空(对账单的收款人除外),就调用 C,只用 C 的值补 B 的空。测试集上整单全对从 83% 提到 90%,回退比例 8%,单张成本从 0.0022 元涨到 0.0024 元;修好了 5 张遮挡单,改坏 0 张。D-safe 再加两条:OCR 平均置信度低于 0.97 也回退;B、C 说法不一致的字段置空转人工。这样静默错误降到 5 个,比 B 的 6 个还少,回退比例 14%。

### Q25 回退信号为什么主要选"字段为空"?阈值怎么定的?
数据显示,B 的 14 个留空错误全在遮挡档,而这些字段 C 几乎都能补对;字段为空是模型自己在说"我不知道",最可靠。阈值在调参集上回放了 144 种配置选出来的,不调 API。但要承认:调参集太容易,B 已经 92.6%,所有配置的最高分都一样(94.4%),最后是靠"回退最少"这条平局规则选的。阈值其实没有被数据确定,需要更难的调参集来验证。

### Q26 融合方案的局限是什么?
① 救不了 B"很自信地错"的情况:照抄的 OCR 错字、越界修正的金额,这时没有任何信号触发回退;② C 补进来的值也可能是静默错误,比如编号少一位;③ 回退时 B、C 是串行的,延迟相加;④ 阈值是在偏容易的数据上选的。一句话讲清:"便宜可靠的先走,它说不确定时才调贵的;两个独立方案说法不一致,就交给人工。"

## 七、工程化

### Q27 接口怎么设计的?
`POST /extract` 用 multipart 上传图片,`method` 参数选 A/B/C/D,默认 D。返回字段、校验错误、所用方案、是否回退、回退原因、耗时、token。错误处理:非 PNG/JPEG 返回 415,超过 5MB 返回 413,文件解码不了返回 400(不信 content_type,真的解一次),方案名不对返回 422,大模型调用失败返回 502(不回传原始错误)。OCR 模型在 lifespan 里启动时加载一次。

### Q28 并发请求时瓶颈在哪?换成 Django 有什么不同?
瓶颈是 CPU 上的 OCR:单张约 19 秒,而且推理加锁串行。LLM 调用可以并发,但受接口限流约束。接口用普通 `def`,FastAPI 会把它放进线程池,不卡住事件循环。Django 是"全家桶",自带 ORM、后台和认证,适合业务系统;FastAPI 更轻,用类型标注加 pydantic 自动校验并生成文档,适合模型推理服务。常见的组合是 Django 做业务后台,FastAPI 做模型服务。

### Q29 别人怎么复现你的环境和实验?
`uv sync` 按 `uv.lock` 装出完全相同的依赖,`requires-python` 限制在 3.11~3.13,因为 Paddle 没有 3.14 的 wheel。实验可以复现:合成数据有固定种子;每次实验结果都带时间戳存进 `results/`,附配置快照(模型、提示词 sha256、数据集);`run_benchmark --reuse` 不用调 API 就能重算指标。

### Q30 你怎么保证测试有效?
除了正常的单元测试,还做了变异测试:故意改坏代码,看测试会不会失败。例如去掉重试,2 个测试失败;把"静默错误"的定义改宽,测试失败;把幻觉率的分母改错,测试失败。测试全部通过不等于测试有效。我还踩过一个坑:测试全部通过,但样本图上的 ¥ 画成了方框,是亲眼看图才发现的。

## 八、银行场景与合规

### Q31 数据不能出内网怎么办?
LLM 调用全部走 OpenAI 兼容接口,换成内网用 vLLM 或 Ollama 部署的开源模型(文本 + 视觉)时,只改 `.env` 里的 `LLM_BASE_URL` 和模型名,代码不用动。OCR 本来就在本地。本项目用合成数据,所以调用了云端;API Key 只放在 `.env`,不提交、不打印,每次提交前我都会扫描待提交的文件里有没有 Key。

### Q32 上线后怎么监控效果?OCR 把金额认错了怎么发现?
监控:回退比例、字段为空率、格式重试率、P95 耗时、单张成本;再按比例抽样人工复核,估计静默错误率。金额错误分层拦截:① schema 严格校验千分位和小数位(`7.003.92` 直接报错);② OCR 读出的金额必须带角分(防止 1.07 被拆成 107);③ 有大写金额的单据,做大小写交叉校验;④ B、C 说法不一致时转人工(D-safe)。目前的漏洞:对账单没有大写,"294 → 2.94"这种错误拦不住。下一步是用明细余额做勾稽校验(上一笔余额减去手续费,应该等于期末余额)。
